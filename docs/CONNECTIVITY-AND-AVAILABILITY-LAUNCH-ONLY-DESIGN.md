# NEXUS — Launch-Only Path: проект требований

Дата: 18.10.2026. Статус: DESIGN / NOT IMPLEMENTED / NOT VERIFIED. Этап A остаётся открытым. Этот документ не разрешает реализацию, изменение launch flow или выполнение тестов.

## 1. Источники и степень подтверждения

Прочитаны [контракт состояний](CONNECTIVITY-AND-AVAILABILITY-CONTRACT.md), [дорожная карта](CONNECTIVITY-AND-AVAILABILITY-ROADMAP.md), [review UNKNOWN/STALE](CONNECTIVITY-AND-AVAILABILITY-UNKNOWN-STALE-REVIEW.md) и [исходный аудит](CONNECTIVITY-AND-AVAILABILITY-PLAN.md). Дополнительный источник — предоставленный в переписке отчёт read-only аудита launch gates: цепочка Play, серверные routes и ссылки на строки.

Технические наблюдения из отчёта используются как предварительные сведения. Исходники в этом документальном этапе повторно не читались, строки не перепроверялись, deployment и выполнение не проверялись. Предлагаемые ниже состояния, результаты и гарантии — требования к будущему пути, не утверждения о наличии этих свойств сейчас.

Приоритет: решения владельца → явно утверждённые положения контракта → предложения последующих review. Ранние предложения исходного аудита о закрытой BETA и запрете launch в MAINTENANCE/UNAVAILABLE не действуют как требования. Предложение UNKNOWN/STALE пока не следует считать окончательно утверждённым изменением существующего контракта.

## 2. Цель, область и неизменные решения

Launch-only запускает выбранную уже установленную пригодную официальную версию, не подготавливая установку путём изменения её файлов. Он не служит обходом updater, авторизации или trust. Наличие отдельной функции с таким названием не доказывает безопасность.

- UNAVAILABLE запрещает install/update, но разрешает запуск пригодной установленной игры при остальных обязательных условиях.
- MAINTENANCE также разрешает пригодный launch, без скрытых загрузок и изменений установки. Install/update и repair со скачиванием или изменением файлов запрещены.
- BETA открыта всем без персональных приглашений. Beta проекта не равен beta-каналу EXE.
- Изменение глобального статуса требует серверной RBAC-проверки владельца либо специально уполномоченного администратора в соответствующей области.
- Обязательные auth, ticket, integrity, signatures, применимый TUF и допустимость версии сохраняются. Новая версия не обязательна только потому, что она существует; обязательное security-ограничение не обходится.

Официальный scope: environment/project/build, выбранная установленная версия и путь, действующая identity generation. Каталог нельзя классифицировать по одному имени или UI-label. Неизвестная принадлежность означает отсутствие доказанного official launch-only пути. На независимые локальные пользовательские проекты новые правила официальной availability автоматически не переносятся.

## 3. Данные, которые должны оставаться независимыми

| Вход | Требуемое свидетельство | Недопустимая подмена |
|---|---|---|
| Scope и identity | Официальный build/environment, установленная версия, текущие user/session generation | Сохранённый nickname, чужой ответ, beta-флаг EXE |
| Локальная готовность | Полный обязательный набор content, assets, libraries, native components, JVM, loader, launch metadata и разрешённых аргументов | Существование папки, READY-label, inventory только модов |
| Состояние установки | Нет опасной незавершённой транзакции и конфликта с updater/import/repair | Удаление lock/journal ради продолжения |
| Availability | Mode и отдельно freshness UNKNOWN/FRESH/STALE | Превращение transport error в UNAVAILABLE либо INSTALL |
| Авторизация | Выполнен действующий контракт сессии и профиля | Кэш профиля как действующий server verdict |
| Ticket | Обязательный ticket валиден по issuer, subject, audience/action, expiry и реально требуемому scope | Формат 64 hex как достаточная проверка допуска |
| Trust/integrity | Установлено, какие доверенные metadata и bytes покрывают конкретные исполняемые компоненты | SHA-256 из недоверенного локального JSON как подпись автора |
| Security version policy | Версия разрешена обязательной политикой, её свидетельства применимы и достаточно свежи | Старый mode availability или один успешный auth-запрос |

Полнота readiness должна задаваться проверенным release/install contract, включая выбранные optional-компоненты и допустимые пользовательские настройки. Нельзя требовать подпись произвольного пользовательского options-файла и одновременно считать неподписанные исполняемые дополнения официально проверенными. Правила для extra mods, пользовательских JVM arguments и mutable config требуют явного scope/security review.

## 4. Целевая последовательность

Все шаги ниже — проект будущего поведения, сейчас ничего не выполняется.

1. **Определить официальный scope.** Зафиксировать выбранную установленную версию, текущий аккаунт/окружение и маршрут действия. Не выбирать новую версию из доступного manifest автоматически.
2. **Получить существующее право сериализации действий.** Проверить отсутствие работающей конфликтующей игры/операции и незавершённой транзакции. Не создавать второй install/update engine. При сомнении перейти к конкретному отказу или отдельному recovery-required, не ремонтировать автоматически.
3. **Read-only readiness.** Проверить безопасные пути, обязательные файлы, локальный runtime/loader и полный применимый inventory/trust evidence. Не вызывать функции, которые устанавливают, мигрируют или восстанавливают данные. Не запускать Java «для проверки» в этом документальном этапе; допустимость такого subprocess в будущей runtime-validation должна быть отдельно определена и доказана.
4. **Обязательные независимые gates.** Проверить авторизацию, профиль, применимые подписи/TUF/security-version evidence по собственным контрактам. Получение обязательных серверных свидетельств допустимо в будущем только через утверждённые endpoints/HTTPS/origin policy, без игровых downloads и изменения установки. Не создавать новый gate только потому, что он упомянут в таблице: обязательность и способ проверки должны быть формально определены.
5. **Сформировать команду из установленного.** Команда, classpath, assets/natives paths, JVM/loader metadata и environment не должны требовать extraction/download/generation в установке. Сборка команды не вызывает installer. Если требуемые natives или другие генерируемые данные не подготовлены — путь не готов, а не разрешён fallback.
6. **Получить обязательный короткоживущий ticket максимально близко к spawn.** Не сохранять его в UI state, командных логах или обычном config. Перед spawn ещё раз проверить identity generation, срок применимости gates и неизменность выбранной версии/локального снимка в пределах доказанного механизма сериализации.
7. **Запустить выбранный локальный executable.** Только при выполненных предусловиях; передача credential дочернему процессу — по отдельному подтверждённому контракту. Если gate истёк или scope изменился, завершить попытку без установки и без автоматического повторного spawn.
8. **Зафиксировать фактический исход.** Process started не равно успешный вход на игровой сервер. Timeout/ошибка не доказывают, что процесса нет; пока ownership/выход не подтверждены, не начинать второй запуск. Снять reservation только по существующему безопасному lifecycle.

Сериализация launcher-операций сама по себе не защищает от внешнего изменения файлов. Нужны отдельно доказанные правила identity/pinning/recheck и границы риска check-to-exec. Не обещать атомарный снимок дерева или полную TOCTOU-защиту.

## 5. Запрещённые побочные действия

Launch-only не имеет fallback в install/update/repair. В его подготовке запрещены:

- установка или обновление игры, modpack, JVM/runtime, loader, libraries, assets, natives и content;
- автоматический repair, восстановление транзакции, rollback/roll-forward, quarantine или удаление файлов;
- применение архива/manifest, подмена установленной версии, запись payload или inventory как «подтверждение готовности»;
- скачивание недостающих файлов, в том числе под видом validate/ensure/prepare;
- миграция options, skin/config/server list и изменение установки ради подготовки запуска;
- автоматическое включение feed, изменение trust stores, подписи, сертификатов, permissions или настроек защиты Windows;
- скрытый переход к альтернативному legacy/library пути при отказе gate.

Read-only этап не должен создавать marker, cache, temp, extracted natives, state journal, новые папки или «исправленные» metadata внутри установки. Если обязательная проверка требует обновления локального trust state по своему контракту, нельзя ни молча писать его через launch-only, ни пропускать проверку: это отдельная операция с отдельным scope/разрешением и доказательствами. Устаревшая security metadata не превращается в пригодную из-за запрета записей.

Граница «без изменения установки» не обещает, что запущенная Minecraft никогда не запишет игровые пользовательские данные. Нужны отдельно утверждённые границы immutable payload, mutable userdata и diagnostics. Логи/credentials/trust persistence вне установки также не объявляются автоматически разрешёнными: их пути и правила требуют отдельного review. До него строгое требование подготовки — без изменений установки; runtime-поведение игры не считать доказанным этим проектом. Запрет загрузок относится к установочным/runtime/content файлам; обязательные auth/ticket/security запросы — иной класс операций и не обходят требования сети.

## 6. Read-only проверка и recovery — разные операции

| Ситуация | Launch-only | Отдельная recovery/install операция |
|---|---|---|
| Полный пригодный payload, нет конфликтов | Проверяет; затем остальные gates | Не нужна автоматически |
| Missing/corrupt runtime, loader, content или natives | Конкретная причина; не скачивать/исправлять | Только отдельно выбранное действие при разрешающем mode и остальных условиях |
| Незавершённая транзакция | Сообщить RECOVERY_REQUIRED, не менять журнал/файлы и не запускать игру из неопределённого состояния | Существующий проверенный recovery engine, отдельное разрешение и политика |
| Lock/ownership неопределённы | Не создавать конкурирующую операцию; не удалять lock | Отдельная диагностика; не выводить безопасность из возраста lock |
| Проверка integrity имеет побочные записи | Не использовать как read-only до доказанного разделения | Переиспользование возможно только после отдельного анализа, не путём обхода защиты |

MAINTENANCE не даёт разрешения на repair/recovery с изменением файлов. Если безопасный запуск требует такого восстановления, попытка заканчивается с причиной, а не обходит recovery. Правила выполнения необходимого recovery в ограничивающих режимах ещё требуется согласовать; этот проект не разрешает его сейчас и не требует удалять существующий механизм.

## 7. Исходы и сообщения

| Причина | Требуемый результат | Сообщение/предел вывода |
|---|---|---|
| Нужных файлов нет | Не запускать; ноль install/update/repair действий; установка сохранена | Указать отсутствующую категорию: runtime/loader/content; не обещать автоматическую загрузку |
| Сессия явно невалидна/истекла | Не запускать; требовать предусмотренную авторизацию | Не трактовать это как UNAVAILABLE проекта |
| Auth-сервис недоступен, обязательную сессию подтвердить нельзя | WAIT_FOR_REQUIRED_EVIDENCE | Не стирать credentials из-за transport failure и не использовать profile-cache как permission |
| Ticket отклонён/истёк/не того scope | Не запускать с ним; отдельная повторная попытка только по контракту выдачи | Не заменять ticket локальным UUID или пустым значением |
| Обязательный ticket нельзя получить | WAIT_FOR_REQUIRED_EVIDENCE; без spawn | «Не удалось получить действующий игровой пропуск»; не обещать offline launch |
| Signature/integrity failure | Отказ по trust/integrity причине | Не лечить автоматическим download или ignore exception |
| Версия запрещена security policy | Отказ, даже если локально полна | Не отменять минимальную версию ради MAINTENANCE/UNAVAILABLE |
| Security evidence отсутствует/просрочено и нет предусмотренного валидного подтверждения | WAIT_FOR_REQUIRED_EVIDENCE либо отказ по её контракту | Не продлевать expiry произвольным grace period |
| Только availability API не отвечает | Сохранить UNKNOWN/STALE и точную причину | Не выдавать это за отсутствие Internet или новый mode |
| Пользователь/окружение/файлы изменились между gate и spawn | Инвалидировать текущую попытку | Не продолжать по старым доказательствам |

Имена исходов здесь концептуальны, не утверждённый API/enum. Для неизвестности требуется причина, отличная от явного security rejection. При ошибке spawn не запускать второй процесс автоматически и не выполнять repair/cleanup для получения «успеха».

## 8. Матрица mode/freshness

«Условный launch» означает всю последовательность раздела 4, полный набор обязательных gates и отсутствие нужды в изменении установки. Никакая строка не отменяет их. Матрица описывает целевой проект, а не текущую поддержку.

| Режим/состояние | Launch-only установленной пригодной игры | Новые install/update/изменяющий repair | Stop и просмотр библиотеки/настроек/диагностики |
|---|---|---|---|
| INSTALL / свежий | Условный launch выбранной установленной версии; не обязательное автообновление | Отдельные действия по действующей policy, не часть launch-only | Доступны по существующим границам |
| MAINTENANCE / свежий | Разрешён при остальных требованиях, без скрытых загрузок/изменения установки | Запрещены | Доступны независимо от mode |
| UNAVAILABLE / свежий | Разрешён при остальных требованиях, без скрытого install/update | Install/update запрещены; изменяющий repair не является обходом, его общая классификация остаётся в review | Доступны независимо от mode |
| BETA / свежий | Условный launch без персонального beta grant | Отдельные действия с общими проверками, не часть launch-only | Доступны |
| UNKNOWN availability | Предлагается не считать само UNKNOWN запретом при независимо подтверждённых gates; зависит от согласования freshness-политики и технических доказательств | Fail-closed: не начинать без свежего допуска | Доступны |
| STALE availability | То же; старый mode не обновляется и его TTL не продлевается | Fail-closed: старое разрешение не даёт новую загрузку | Доступны |

UNKNOWN/STALE не являются административными modes и не превращаются в UNAVAILABLE. Отсутствие required auth/ticket/security evidence не превращается в ALLOW. Если availability и обязательный security verdict пока технически сцеплены, неизвестность последнего остаётся блокером: нельзя удалить `build_access()` как самостоятельное исправление. Сначала доказать, что заменяющий/разделённый путь сохраняет все обязательные проверки, затем получить отдельное разрешение на изменение.

В текущем контракте freshness official launch UNKNOWN/STALE отмечена как отдельное предложение на review; этот дизайн не заменяет её молча. Полноценный offline launch не подтверждён. При обязательном сетевом ticket полная потеря сети может остановить запуск независимо от availability.

## 9. Все маршруты действий

| Поверхность | Требование будущего проекта | Предварительное наблюдение из отчёта, не повторная проверка |
|---|---|---|
| Native official Play | Общая граница launch-only; UI enable не выдаёт permission | Native вызывает CoreLauncher; allowed может блокировать Play до worker |
| HTML official Play | Тот же policy/снимок и gates; ограниченная проекция без секретов | `play-server` идёт через native services._play |
| Retry/download retry | Явно различать повтор launch и install; при UNKNOWN/STALE/ограничивающем mode не переходить к install | Retry снова вызывает _play; существующий Play не read-only |
| Repair | Отдельное действие, не fallback launch; режим проверяется до изменений | Repair вызывает updater напрямую; эквивалентная availability-проверка не подтверждена |
| Пользовательские экземпляры/library/test-launch | Сохранять собственную политику; official-linked ресурсы явно классифицировать | Library worker имеет другую цепочку без build-access, но вызывает общий core.launch с установкой |
| Legacy-клиенты | Определить поддержку по конкретной версии; не использовать как bypass | В Tkinter-исходнике иной worker и нет переданного ticket supplier; поведение распространяемых EXE неизвестно |
| Stop/running game | Сохранить доступ к существующему управлению процессом; не убивать игру из-за нового status | Состояние кнопки и alternate actions нуждаются в совместном review |

Ни отсутствие build-access, ни существование общего core не доказывают одинаковую безопасность всех путей. Безопасность official-linked library/import routes пока не установлена. Отдельный launch-only должен проходить общую проверяемую границу; дублирующий updater не создаётся.

## 10. Границы доверия

| Объект | Требование | Что не подтверждено / не следует утверждать |
|---|---|---|
| Игровой payload и зависимости | Полный применимый inventory и обязательное доказательство происхождения/целостности | Хеши managed modpack не покрывают автоматически JVM/assets/loader/extra mods |
| Launcher package/bootstrap | Сохранить existing signature/inventory/slot и path boundaries | Подпись launcher-пакета не является подписью игровых manifests |
| Release signatures | Проверять соответствующий подписанный объект и правильный trust scope | SHA-256 без доверенной подписи не подтверждает автора; наличие модуля не доказывает coverage |
| TUF v2 | Сохранить обязательные root/role/expiry/replay правила там, где применим действующий контракт | Изолированный metadata verifier не доказывает проверку target bytes и безопасности игровой версии |
| Session/ticket | Сохранить серверную актуальность, identity binding, expiry, audience/action и погашение по реальному контракту | Ticket не подтверждает integrity/допустимость версии; интеграция игровой стороны не доказана |
| Security version policy | Отдельно установить минимальную безопасную версию/отзыв, источник доверия и срок evidence | Mode availability не заменяет emergency security deny; механизм нельзя выдумать как уже реализованный |
| Глобальная availability | Только серверный RBAC меняет статус; client cache только вспомогателен | Локальный админ-флаг, UI, public URL или health success не являются полномочием |

Stable/beta trust stores, TUF и legacy metadata не объединяются; bootstrap feed не включается. Public URL открытой BETA не является защищённым закрытым доступом. Нельзя обещать отзыв уже скачанных байтов или безопасную выдачу всех ресурсов только по одному статусному endpoint.

## 11. Проверяемые инварианты для будущих синтетических тестов

Это только описания, тесты не написаны и не выполнялись. Будущие pure tests смогут проверить модель и intents, но не доказать отсутствие реального I/O сторонней библиотеки или корректность Windows/deployment.

| Инвариант | Будущий синтетический сценарий / ожидаемое свидетельство |
|---|---|
| Нет установочных intents | Для всех шести строк матрицы launch-only не создаёт install/update/repair/download/apply intents |
| Missing files не исправляются | Каждый missing runtime/loader/content/assets/native случай даёт конкретную причину и ноль mutation intents |
| Recovery не маскируется под validate | Незавершённая транзакция/неопределённый lock: RECOVERY_REQUIRED/отказ, journal не объявляется исправленным |
| Gates независимы | Status API failure при валидных required evidence не превращается в UNAVAILABLE; expired required evidence отдельно блокирует |
| Owner semantics сохранены | MAINTENANCE/UNAVAILABLE пригодная версия + все gates: условный launch; BETA без приглашения имеет тот же общий допуск |
| Нет обновления из наличия новой версии | UPDATE_AVAILABLE + пригодная допустимая старая версия: выбранная версия не заменяется; security deny всё равно блокирует |
| Scope/session race | Поздний ответ, logout/account/environment смена перед spawn: попытка инвалидируется, ticket не переносится |
| Нет grace обязательных свидетельств | Истечение ticket/TUF/security перед spawn: не ALLOW из-за сети, last mode или grace availability |
| Команда локальна и безопасна | Нужда в extraction/generation/download при сборке команды даёт отказ, не auto prepare; credentials отсутствуют в UI/log intents |
| Одна попытка — один lifecycle | Spawn timeout/unknown exit не порождает retry worker или второй process intent |
| UI не обходится | Native/HTML/Retry дают одинаковый результат для одинакового official snapshot; repair/library не становятся fallback |
| Stop не зависит от status | RUNNING + любой mode/freshness сохраняет stop; network transition не создаёт terminate intent автоматически |

Позднее отдельно потребуются разрешённые filesystem/process/transport проверки на синтетических данных с независимым наблюдением за отсутствием изменений установки. Сейчас fixtures, workers, интеграционные тесты и test harness не создаются. Успех pure tests не позволит назвать launch-only безопасным без доказательства реальных зависимостей.

## 13. Условия дальнейшего допуска

Чтобы говорить о готовности launch-only к реализации, нужны: review UNKNOWN/STALE policy; полный scope/readiness/trust/security контракт; доказанная возможность отделить command/spawn от install/update/repair и миграций; определённая граница допустимых runtime/userdata записей; доказанный session/ticket/server flow; согласованное поведение при каждом missing/expired evidence; перечень поддерживаемых UI/legacy путей и план их проверки.

Без этих доказательств launch-only остаётся NOT VERIFIED. Самостоятельное удаление `build_access()` не предлагается как исправление. Сначала отдельно разрешённое исследование перечисленных зависимостей, затем отдельное разрешение на локальные изменения и тесты. Ни принятие дизайна, ни будущие pure tests не закрывают автоматически этап A и не разрешают B, production или публикацию.
