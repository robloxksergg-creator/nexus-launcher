# NEXUS — review политики launch при UNKNOWN / STALE

Дата: 18.10.2026. Статус: предложение владельцу, не принятое за него решение. Только документальный review. Этап A не закрыт, переход к B не разрешён.

## 1. Неизменные решения и область

- UNAVAILABLE запрещает install/update, но разрешает launch пригодной установленной игры при остальных обязательных условиях.
- MAINTENANCE разрешает такой launch без скрытых загрузок и изменения установки; install/update и repair со скачиванием или изменением файлов запрещены. При missing files — конкретная причина и завершение попытки без изменения установки.
- BETA открыта всем желающим без персональных приглашений. Beta-режим проекта не является beta-каналом EXE.
- Мутации глобального статуса выполняют владелец и специально уполномоченные администраторы через серверный scoped RBAC.
- Авторизация, обязательные tickets, целостность, подписи, TUF и ограничения допустимости версии не обходятся. Availability не заменяет эти проверки.

Review относится только к новому запуску официальной уже установленной игры. Независимые локальные пользовательские проекты не получают новые ограничения. Уже работающая игра не завершается из-за UNKNOWN/STALE; существующее действие stop и просмотр библиотеки, настроек и диагностики остаются доступны.

## 2. Раздельные свидетельства

| Измерение | Что требуется различать | Что не является заменой |
|---|---|---|
| Наличие установки | Файлы/каталог существуют | Само наличие не доказывает completeness, integrity или доверие |
| Локальная готовность | Нужные content, JVM, loader и зависимости пригодны; нет опасной незавершённой транзакции | Один label READY или отсутствие ошибки в прошлом не является полным доказательством |
| Freshness availability | UNKNOWN — нет принятого снимка; STALE — снимок был, но срок его применимости закончился | Последний mode не превращается в актуальный и не разрешает новые downloads |
| Авторизация | Действующая по своему контракту сессия текущего пользователя/окружения | Кэш имени/профиля, наличие token-файла и network success не доказывают авторизацию |
| Игровой ticket | Если обязателен: подлинность, срок, audience/action/subject и применимые scope/one-time правила | Availability response не является ticket; существование ticket не доказывает полноту его security-проверок |
| Целостность и происхождение | Обязательные проверенные metadata/signatures и bytes согласно применимому trust-контракту | SHA-256 без доверенной подписи не доказывает автора |
| Security-ограничения версии | Установленная версия допускается обязательной независимой политикой, включая отзыв, минимальную версию и freshness, если это требуется | Старый INSTALL/BETA/UNAVAILABLE/MAINTENANCE не доказывает допустимость версии |
| Connectivity и конкретные API | Локальная связь, NEXUS reachability, auth/status/ticket/security endpoint outcomes — разные наблюдения | DNS/TLS/HTTP ошибка одного ресурса не доказывает отсутствие Internet или новый режим проекта |

У каждого свидетельства собственные scope, источник доверия, expiry и условия повторного использования. Истечение availability не продлевает ticket или security metadata; свежий ticket сам по себе не продлевает TUF. Применимость TUF к конкретному launch-пути должна быть установлена его контрактом: review не вводит требование загрузить все update metadata при каждом запуске и не отменяет ни одной уже обязательной проверки.

## 3. Сравнение вариантов

| Вариант | Поведение UNKNOWN / STALE | Преимущества | Риски / ограничения | Вывод |
|---|---|---|---|---|
| Всегда ждать свежий availability | Любой новый official launch блокируется до status API success | Простая общая UI-модель; нет неопределённого mode | Сбой информационного статуса блокирует исправную игру даже при валидных launch/security evidence. Все четыре согласованных режима уже допускают launch; fresh mode не добавляет самостоятельного запрета | Консервативный по доступности, но избыточный как постоянная цель при нынешней семантике |
| Launch только по последнему mode с grace period | STALE допускается некоторое время; UNKNOWN запрещён | Меньше блокировок после краткого сбоя | Нужны произвольные grace TTL/доверие к часам; разные права первой и повторной установки клиента; риск ошибочно продлить обязательные security/auth evidence | Не рекомендуется как минимальная модель |
| Launch только по наличию файлов | UNKNOWN/STALE игнорируются вместе с остальными сетевыми проверками | Высокая видимая доступность | Обход обязательной авторизации/tickets/отзыва/версии/trust; повреждённая или неполная установка может стартовать | Недопустим |
| Независимые launch-gates | Свежесть availability не является отдельным gate launch; все обязательные независимые проверки остаются | Не превращает сбой status API в искусственный запрет; соответствует разрешённому launch во всех четырёх режимах | Требуется доказать разделение status и security/auth, отсутствие скрытых downloads; полная недоступность сети всё ещё может помешать обязательному ticket | Рекомендуемый минимальный целевой вариант, только после review и подтверждения предпосылок |

Grace для availability не решает неизвестность security-политики. Не вводить новый общий срок «можно играть N дней» и не увеличивать expiry обязательных свидетельств ради доступности.

## 4. Рекомендуемая политика для согласования

**UNKNOWN/STALE availability само по себе не запрещает launch уже установленной пригодной игры. Попытка допускается только после успешного выполнения всех обязательных независимых launch-gates и без установки, обновления или изменяющего repair.**

Это предложение изменяет только потенциальную роль freshness availability в launch, а не утверждённые режимы и не действующий контракт до согласования. В текущем контракте WAIT_FOR_EVIDENCE для official launch UNKNOWN/STALE отмечено как предложение на review; этот файл предлагает альтернативу, но не редактирует и не активирует её.

Формально для рассматриваемого пути:

`LAUNCH_ELIGIBLE = official_scope_known AND installed_ready AND no_conflicting_or_unsafe_transaction AND required_auth_valid AND required_ticket_valid AND required_integrity_and_trust_valid AND required_security_policy_valid AND no_install_update_or_repair_needed`.

Значения required-gates определяются их собственными действующими контрактами. Отсутствие подтверждённого требования не означает «проверка не нужна»: если нельзя установить обязательность и корректно проверить её, безопасный путь не доказан. Нельзя объявлять все gates true на основании одного ticket или одной локальной проверки.

F_availability не входит в эту формулу как самостоятельный gate только при подтверждённом разделении availability и обязательной security/authorization информации. Если один ответ содержит также обязательный security verdict, нельзя игнорировать истечение этого verdict вместе с availability. Такая зависимость остаётся блокером до отдельного доказательства.

### Последовательность решения без побочных действий установки

1. Определить официальный scope, текущего пользователя/окружение и запрашиваемую установленную версию. Не использовать чужой или поздний ответ.
2. Проверить локальную готовность и незавершённые транзакции существующими безопасными средствами. При missing files не скачивать, не запускать repair/update, не изменять установку.
3. Проверить все обязательные auth/ticket/integrity/trust/version evidence по их срокам и scope. Сетевое получение обязательного ticket или проверки, если требуется действующим контрактом, не является загрузкой игровых файлов, но не должно скрыто вызывать install или менять установку. Сейчас запросы не выполняются.
4. Если required evidence отвергнуто — отказ с конкретной причиной. Если его невозможно подтвердить — WAIT_FOR_REQUIRED_EVIDENCE с конкретной категорией. Это концептуальное обозначение результата review, не существующий enum и не переименование mode.
5. При успешных gates и UNKNOWN/STALE availability разрешить launch с предупреждением об отсутствии актуального статуса. Старый mode остаётся исторической подписью, не становится FRESH или INSTALL.
6. Availability refresh может выполняться отдельно по будущему согласованному monitor-контракту; он не является условием запуска при доказанном выполнении остальных gates. Восстановление сети само не запускает игру, установку или обновление.

Если архитектура сегодня делает обязательный fresh build-access частью серверной авторизации launch, этот review не разрешает удалить вызов или проигнорировать отказ. Сначала нужно определить, является ли это самостоятельным security gate или техническим сцеплением с availability, и отдельно согласовать изменение. Пока разделение не доказано, нельзя заявлять поддержку рекомендуемого пути.

## 5. Таблица исходов

| Вход | Рекомендуемый исход нового official launch | Объяснение пользователю |
|---|---|---|
| UNKNOWN availability, все required-gates успешно проверены | Допустить launch без install/update/repair | «Статус проекта сейчас не подтверждён. Установленная игра готова к запуску.» |
| STALE availability, все required-gates успешно проверены | То же; не продлевать срок последнего снимка | «Статус проекта устарел. Запускаем установленную версию.» |
| UNKNOWN/STALE, missing content/JVM/loader | Не запускать; сохранить установку | «Для запуска не хватает файлов. Статус установки не подтверждён; загрузка не начата.» |
| UNKNOWN/STALE, обязательный ticket истёк и получить новый нельзя | Ждать требуемое свидетельство, без launch | «Не удалось получить действующий игровой ticket. Повторите попытку позже.» |
| UNKNOWN/STALE, session rejected или недостаточная обязательная авторизация | Не запускать по auth-причине | Конкретное требование входа/подтверждения; не «Проект недоступен» |
| UNKNOWN/STALE, signature/integrity failure или запрещённая версия | Отказать по security-причине | Конкретная безопасная причина; не выполнять обновление автоматически |
| UNKNOWN/STALE, обязательная security policy просрочена/неизвестна | Не запускать до выполнения её собственного контракта | «Не удалось подтвердить обязательную проверку безопасности.» |
| Status API 503, обязательные launch-сервисы работают | Не распространять 503 на остальные gates; применить их результаты | «Не удалось обновить статус проекта», без ложного offline/UNAVAILABLE |
| Полная потеря сети и отсутствует required evidence | Не заявлять offline launch; не обходить обязательные проверки | Указать недостающую проверку, а не выдуманный mode |
| Уже RUNNING | Не завершать игру из-за status failure; stop доступен | Некритичный banner, без повторяющихся сообщений |

Новые install/update при UNKNOWN/STALE остаются fail-closed. Изменяющий repair также не является обходом отсутствующего допуска. Read-only диагностика не получает право чинить установку. Это предложение не вводит автозагрузки даже если старый кэш говорил INSTALL/BETA.

## 6. Границы безопасности и остаточные риски

Все четыре согласованных mode сейчас допускают пригодный launch при прочих условиях. Поэтому отдельная свежесть mode не добавляет launch-security решения; безопасность должна обеспечиваться соответствующими обязательными механизмами. Это вывод из документальной семантики, а не доказательство текущего сервера.

Если требуется возможность экстренно запретить исполнение уязвимой версии, она должна быть явно описана как обязательная security-политика со своим trust/freshness/revocation контрактом. Нельзя молча придать MAINTENANCE или UNAVAILABLE значение запрета launch, противоречащее решениям владельца. Полномочия такого security-механизма и его реализация этим review не создаются.

Риски остаются: скомпрометированный/непроверенный локальный cache; смена файлов между проверкой и launch; недоказанный version revocation; ticket без нужного scope; скрытая загрузка runtime; сцепление auth и build-access. Review не обещает устранить TOCTOU или отозвать уже скачанные байты. Подписи/TUF/HTTPS/origin, slots/rollback, ownership установщика и stable/beta trust stores не меняются. Bootstrap feed не включается.

Нет утверждения, что существующий ticket содержит security verdict, что TUF уже охватывает все игровые файлы или что локальный integrity check достаточен для всех зависимостей. Отсутствие таких доказательств нельзя заполнить предположением.

## 7. Что решается документально, что остаётся неизвестным

| Вопрос | Документальный выбор владельца | Неизвестное и отдельное требуемое действие |
|---|---|---|
| Freshness availability как launch gate | Принять/отклонить независимые launch-gates вместо blanket WAIT_FOR_EVIDENCE по одному F_availability | После выбора отдельно разрешить аудит зависимостей до изменения кода |
| Никакого grace security/auth | Зафиксировать, что availability outage не увеличивает сроки обязательных свидетельств | Точные текущие auth/ticket/security expiry и поведение clocks не проверялись |
| Readiness без downloads | Утвердить требование запуска только имеющейся пригодной версии | Отдельно исследовать launch/content/JVM/loader/repair/recovery пути и гарантии отсутствия изменений установки |
| Обязательная security-политика | Определить необходимые минимальные версии, отзыв, доверие, freshness и реакцию на отсутствие evidence | Неизвестно, что реально реализовано и применимо к launch; никакой новой системы сейчас не строится |
| Tickets и серверная авторизация | Зафиксировать сохранение действующих обязательных требований | Не подтверждены build/version binding, одноразовость, revocation, dependencies на build-access и соответствие production |
| TTL/часы | Согласовать отдельные lifetimes для availability и required evidence, restart/skew правила | Реальное monotonic/persistence/серверное время требует отдельно разрешённого исследования/тестов |
| Старые клиенты и обе оболочки | Определить поддерживаемые версии, UI причины, совместимость mode/launch semantics | Не подтверждены реальные EXE и каждый альтернативный action path |
| Серверные гарантии | Определить необходимые read/write/RBAC/audit/CAS свойства | Локальные исходники не подтверждены как production/staging; write endpoint описан в аудите как закрытый |

Этот этап не читает исходники, не проверяет endpoints и не выполняет перечисленные технические действия. Сначала требуется отдельное разрешение на конкретный read-only технический аудит; код, тесты, live-запросы и infrastructure changes требуют собственного scope.

## 8. Предложение решения для review владельца

Предлагается согласовать следующее: «Для официальной пригодной установленной игры UNKNOWN/STALE только статуса availability не является самостоятельным запретом launch. Все обязательные auth/ticket/integrity/signature/TUF/version/security проверки выполняются по собственным контрактам. Если обязательное свидетельство отсутствует, отвергнуто или просрочено без разрешённого способа подтверждения, launch не выполняется с конкретной причиной. Install/update/изменяющий repair без свежего допуска не начинаются. Поддержка такого пути требует отдельного доказательства разделения механизмов и отсутствия скрытых загрузок».

До явного решения владельца это рекомендация, не принятое изменение контракта. Даже согласование текста не доказывает возможность работы без сети, не закрывает технические блокеры и не разрешает переход к B. Если документального разделения security и availability недостаточно, реализация остаётся заблокированной до отдельного исследования; нельзя ослаблять обязательный gate ради доступности.
