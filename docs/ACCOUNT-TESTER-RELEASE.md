# NEXUS account and tester foundation — 2026-10-08

## Architecture and implementation sequence
The launcher is Python/PySide6 6.8.3, Qt WebEngine, restricted loopback assets and same-origin command navigation, not Electron/Tauri. `nexus_launcher/tester_main.py` creates the existing NexusLauncher services and DesignHost. Native AuthState owns credentials and session transitions; the renderer receives display name and username only. The UI reuses theme_tokens/presentation_style, NexusLogin and RegistrationDialog. Studio and Academy keep their existing service/model/storage owners. Native chrome remains the v30 Windows/Qt-owned maximize/restore implementation.

The backend is the existing `D:/nexus-work/website_NexusMC` React/Vinext Cloudflare application, D1 and Drizzle SQL migrations. Existing routes are `/api/auth/email/request-code`, `/api/auth/register`, `/api/launcher/auth/login`, `/api/launcher/profile`, `/api/launcher/auth/logout`. Server hashing remains versioned scrypt with pepper, random salts, bounded KDF concurrency and migration of legacy hashes. Existing D1 rate limits, email challenges, device rules and HTTP-only browser sessions are reused. Desktop bearer tokens are random; only their hashes are stored server-side, and plaintext tokens live in Windows Credential Manager, not localStorage/files. Existing browser and desktop sessions remain separate.

Phase 1 added migration 0018 and account fields username, display_name, avatar, updated_at, status and tester. Existing nickname becomes the initial normalized username; this preserves Minecraft identity/device policies. Unique case-insensitive username and normalized email indexes reject conflicts rather than merging accounts. Migration runs against the existing users table, no second account database. Nullable additive fields permit existing seed/import tooling; authoritative registration always supplies username/display name/update time. Reserved names/input limits live in db/accountPolicy.ts.

Phase 1 validation completed before route integration: D1 migration and policy tests, TypeScript and scoped lint passed. Phase 2 integrated new fields into registration/session profiles, active-status enforcement and server tester gating. Browser authentication also honors status. Account responses are no-store. Real delivery is configured through EMAIL_FROM and RESEND_API_KEY; EMAIL_DELIVERY=resend is the production/public staging mode. Local/staging mocks require explicit sink injection inside tests and cannot disclose codes through an HTTP endpoint. Actual code storage, expiry, attempts and consumption remain exercised by the isolated test harness.

Phase 3 introduces a separate tester startup gate: unknown session never reveals launcher UI; network/server/expired-session/rejected-login states offer recovery. Periodic restore checks expiry. Staging and production Credential Manager namespaces are separate; beta game/project data is under %LOCALAPPDATA%/NEXUS Tester/beta. Logout clears only authentication. When offline logout cannot reach the server, the local token is removed and the connection failure is shown; remote revocation is not falsely claimed. Existing per-device one-account policy remains.

Phases 4–6 use existing PyInstaller and verified bootstrap installer. `assets/tester-release.json` is beta configuration; `nexus_launcher/build_tester_release.py` rejects localhost/production/missing tester identity. Stable assets/release.json is unchanged. A staged asset copy supplies beta metadata and Windows version info; application, package and UI version are 1.0.0-beta.1. No server private keys or account fixtures are bundled. Logs contain lifecycle categories, not passwords/tokens/email/codes. Existing update infrastructure remains disabled for this beta. Draft manifest includes hashes, sizes, version, channel, signed=false and available=false.

## Candidate, not published release
Artifacts are in D:/nexus2/tester-releases/1.0.0-beta.1. This is an unsigned private candidate, not a completed public tester rollout. No live account was registered, no personal email was used, no email was sent by these tests, no remote D1 schema was changed and no GitHub/production release was published. The user will connect a separate test mailbox later. Current remote staging may still return the old profile without tester fields; this candidate intentionally will not bypass the gate.

Before tester distribution: back up/check staging D1, apply 0018 with the existing migration mechanism, deploy the prepared backend through its existing hosting workflow, configure server-side NEXUS_TESTER_ONLY=true, PASSWORD_PEPPER, EMAIL_DELIVERY=resend, verified EMAIL_FROM and RESEND_API_KEY, then enroll specific tester accounts in users.tester through an authorized administrative operation. Never grant tester status from a registration payload/client. wrangler.staging.jsonc prepares the flag, production configuration is unchanged. The site has existing .openai hosting metadata; deployment must use its configured hosting path rather than silently replacing that deployment.

After mailbox setup verify actual delivery, registration, login, logout, restart persistence and session expiry on remote staging with the installed EXE; confirm Studio, Academy, save and preview. Only after acceptance create a controlled prerelease with the attached notes and checksums. Signing uses a real certificate when available; this candidate is unsigned and Windows SmartScreen may warn.

The installer reuses the existing bootstrap: verified payload, explicit install directory, recovery copy of previous executable, no deletion of accounts/projects/game installations. Installation and launch are tested by CLI in an isolated folder. It is not yet an MSI/Inno installer with Start Menu/uninstall integration. One-file client startup includes extraction time; API 127.0.0.1 in the shell is a packaged read-only asset server, not a development/auth backend.
