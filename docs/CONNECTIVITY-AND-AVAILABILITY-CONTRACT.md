# NEXUS: контракт состояний и действий — этап A

Дата: 18.10.2026. Статус: проект для review. Формализация требований, не реализация и не разрешение на тесты. Полная готовность этапа A не объявляется: ниже сохранены открытые решения.

Источники: [исходный аудит](CONNECTIVITY-AND-AVAILABILITY-PLAN.md) и [дорожная карта](CONNECTIVITY-AND-AVAILABILITY-ROADMAP.md). Решения владельца и уточнения roadmap имеют приоритет над ранними предложениями аудита о закрытой BETA и запрете запуска в UNAVAILABLE/MAINTENANCE. Исходный аудит сохранён; roadmap точечно синхронизирован с решением MAINTENANCE. Локальный серверный код не считается подтверждённой копией production/staging.

## 1. Область и обязательные решения

Контракт доступности применяется к официальной сборке в явном scope `environment/projectId/buildId`. Открытая BETA проекта не является beta-каналом EXE.

- UNAVAILABLE запрещает установку и обновление, но разрешает запуск уже установленной игры при выполнении остальных условий запуска.
- BETA открыта всем желающим. Персональный beta grant или приглашение не требуется; общие требования к аккаунту, безопасной выдаче файлов и запуску сохраняются.
- Глобальный статус меняют владелец и специально уполномоченные администраторы: каждую мутацию проверяет серверный RBAC в соответствующем scope. Название ещё не существующей permission не назначается этим документом.
- MAINTENANCE — вопрос запуска решён владельцем: новая установка, update и repair со скачиванием или изменением файлов запрещены; запуск установленной и пригодной игры разрешён при всех остальных требованиях. Скрытая загрузка недостающих файлов и автоматический install/update запрещены. При отсутствии необходимых файлов показать конкретную причину и закончить попытку без изменения установки. Независимые обязательные проверки безопасности, авторизации, целостности и допустимости версии сохраняются. Stop работающей игры и просмотр настроек/диагностики не зависят от режима.

Локальные пользовательские проекты не получают новые ограничения из этой матрицы. Для них сохраняется существующая политика; если они используют официальные ресурсы, серверные правила выдачи именно этих ресурсов остаются обязательными. Неизвестный тип проекта нельзя молча объявить официальным и заблокировать либо пользовательским и разрешить: требуется классификация до применения этой политики.

## 2. Входной снимок состояния

Это концептуальные типы для будущей чистой модели, не новые API или утверждение об имеющихся enum. Входные данные включают scope, generation окружения/сессии, номер запроса, monotonic time и происхождение наблюдения. Не включают токены, пароли, коды и секретные URL.

| Измерение | Значения | Смысл и ограничения |
|---|---|---|
| Connectivity C | UNKNOWN, LOCAL_LINK_PRESENT, LOCAL_LINK_ABSENT | Только локальная связь по проверяемому системному источнику; наличие link не доказывает Internet |
| NEXUS reachability N | UNKNOWN, CHECKING, REACHABLE, UNREACHABLE | Состояние конкретного origin и проверяемого service path; не всех сервисов сразу |
| Outcome конкретного API Q | NONE, SUCCESS, TRANSPORT_FAILURE, TLS_FAILURE, PROTOCOL_FAILURE, AUTH_REQUIRED, FORBIDDEN, RATE_LIMITED, SERVICE_FAILURE | Результат одной операции; хранится отдельно от глобального N |
| Authorization A | UNKNOWN, CHECKING, AUTHENTICATED, SIGNED_OUT, REJECTED, EXPIRED | Подтверждение сессии; сохранённый профиль не равен AUTHENTICATED; offline не равен logout |
| Availability mode M | INSTALL, MAINTENANCE, UNAVAILABLE, BETA или отсутствует | Полномочное значение только из валидного серверного контракта для данного scope |
| Freshness F | UNKNOWN, FRESH, STALE | UNKNOWN: нет принятого валидного снимка. STALE: снимок есть, но больше не разрешает новые действия по свежести |
| Engine E | NOT_INSTALLED, CHECKING, PREPARING, DOWNLOADING, VERIFYING, APPLYING, FINALIZING, READY, UPDATE_AVAILABLE, REPAIR_REQUIRED, FAILED, RUNNING | Используются существующие понятия install engine; доступность не переписывает delivery state |
| Local readiness L | UNKNOWN, VERIFIED_READY, NEEDS_FILES, UNSAFE_OR_INCOMPLETE | Отдельно от версии: UPDATE_AVAILABLE может иметь пригодную установленную версию; наличие каталога не доказывает готовность |
| Operation O | IDLE, ACTIVE, RECOVERY_REQUIRED | Сериализация действий и незавершённая транзакция; connectivity не очищает lock или журнал |
| Game G | NOT_RUNNING, RUNNING, EXIT_UNKNOWN | Фактическое состояние процесса, отдельно от E; stop не должен зависеть от свежести статуса |

N хранится по origin, Q — по API/операции. Например, успешный health и 503 install API совместимы; нельзя заменить все измерения одним ONLINE. Для фаз APPLYING/FINALIZING политика завершения определяется engine, а не новым enum сети.

## 3. События и допустимые переходы

Любое событие сначала проверяется на принадлежность scope/generation/request. Поздний ответ предыдущего аккаунта или окружения игнорируется для текущего решения; секреты в событие не помещаются. Сам факт события не запускает установку.

| Событие | Допустимый переход | Запрещённый вывод/эффект |
|---|---|---|
| Старт процесса | C/N/A/F = UNKNOWN до соответствующих наблюдений; E/L определяются существующей проверкой | Восстановить разрешение из старого кэша или default OPEN |
| Валидный системный сигнал | C → LOCAL_LINK_PRESENT/ABSENT; недоступный backend оставляет UNKNOWN | Вывести работоспособность NEXUS из link present |
| Начало bounded probe | N → CHECKING; сохранить последнее наблюдение отдельно | Выдать install capability или сбросить auth |
| Подтверждённый успех probe | N → REACHABLE по правилам hysteresis | Объявить все API исправными, F свежим или A авторизованным |
| Подтверждённый transport/probe failure | N → UNREACHABLE для этого origin; Q отражает причину | Перевести C в LOCAL_LINK_ABSENT только по DNS/TLS/HTTP ошибке |
| 401/403/429/5xx конкретного API | Q → соответствующая категория; явный authoritative session rejection меняет A | Любой 403 трактовать как logout, 429 как offline, 5xx как закрытие проекта |
| Начало auth-проверки | A → CHECKING; UI может отдельно хранить последний профиль | Разрешить действия одним сохранённым именем пользователя |
| Валидный auth success текущей generation | A → AUTHENTICATED | Получить admin permission или персональный beta grant из этого факта |
| Logout/подтверждённое истечение/отклонение | A → SIGNED_OUT/EXPIRED/REJECTED; инвалидировать account-bound допуски | Перенести допуск в другую сессию |
| Transport failure auth-запроса | Q меняется; подтверждённость A оценивается по сроку сессии и evidence, не по сети | Стереть credentials или объявить их неверными без session rejection |
| Валидный status response | F → FRESH, M → подтверждённый режим, обновить revision и срок | Принять неизвестный ID/режим/schema как INSTALL |
| Подтверждённый переход в MAINTENANCE | Запретить новые install/update и изменяющий repair; для установленной пригодной игры сохранить условный launch по остальным требованиям | Превратить maintenance в общий запрет launch, скрытый download или автоматический install/update |
| Истёк допустимый срок/нарушена гарантия времени | FRESH → STALE; сохранить M только для отображения | Продлить разрешение фактом health success |
| Ошибка status API | Без валидного снимка F остаётся UNKNOWN; прежний FRESH действует только до своей доказанной границы, затем STALE | Превратить ошибку в новый режим или бессрочно продлить TTL |
| Смена scope/environment | Новые N/F observations для нового scope; старые ответы не принимаются | Переносить production permission/данные доверия в staging или обратно |
| Смена аккаунта | Инвалидировать account-bound evidence, увеличить session generation | Использовать ticket предыдущего пользователя; публичный status scope не становится персональным grant |
| Заявка действия | При IDLE вычислить решение; только при выполненных условиях передать engine | Начать запись/загрузку до допуска или параллельно существующей транзакции |
| Engine progress/success/error | E/O меняются только по существующему engine/процессу | Status callback UI не может открыть запрещённое действие |
| Потеря сети/смена режима во время операции | Обновить policy snapshot; не начинать следующий запрещённый сетевой шаг, останавливаться лишь в безопасной точке engine | Убить atomic apply, очистить journal или начать новый recovery автоматически |
| Игра завершилась | G/E обновить по подтверждённому исходу, затем переоценить UI | Считать один timeout доказательством завершения процесса |

M может меняться между любыми четырьмя значениями только по валидному новому серверному статусу. UNKNOWN/STALE не являются мутациями M. После восстановления сети сначала обновляются нужные evidence; install/update/repair автоматически не возобновляются.

## 4. Свежесть и валидация статуса

Будущему контракту нужны schema version, scope, revision, mode, issuedAt/validUntil и ограниченная plaintext причина. Наличие таких полей в текущем production не подтверждено. Точные TTL, правила допустимого clock skew, server cache и polling — неутверждённые параметры из roadmap, не окончательные числа данного контракта.

FRESH означает одновременно: schema/тип/enum/ID валидны; origin и environment соответствуют политике; срок не истёк; локальное monotonic elapsed не превысило согласованную верхнюю границу; revision не ниже принятой в том же scope; одинаковая revision не имеет другого содержимого. Изменение mode требует новой revision. Повтор идентичной revision не продлевает абсолютный срок её действия.

Синтаксически ошибочный, противоречивый или чужой ответ не заменяет последний принятый снимок, не продлевает его жизнь и создаёт диагностируемый отказ. Отсутствующий снимок остаётся UNKNOWN; прежний станет STALE по своей границе. Без подтверждённого freshness-контракта нельзя утверждать, что существующий ответ уже даёт доказанный FRESH.

После restart локальный кэш отображает только последнее известное значение; разрешение требует нового принятого evidence. Механизм хранения revision/защиты от локального вмешательства и восстановления после повреждения ещё предстоит спроектировать; серверная проверка не может зависеть от честности клиентского кэша. Availability revision не подменяет TUF replay/expiry protection.

## 5. Формальный результат проверки действия

Результат — один из `ALLOW_CONDITIONAL`, `DENY`, `WAIT_FOR_EVIDENCE`, `OUTSIDE_AVAILABILITY_SCOPE` с ограниченным reason code. Это проект типов, не уже реализованные API. Прежний OWNER_DECISION_REQUIRED для MAINTENANCE launch больше не применяется: решение владельца зафиксировано.

- ALLOW_CONDITIONAL: режим допускает действие; все прочие клиентские и серверные предусловия ещё обязаны выполняться. UI enable не является серверной capability.
- DENY: известная политика/проверка запрещает действие; не запускать его побочные эффекты.
- WAIT_FOR_EVIDENCE: не хватает подтверждения, не считать это новым запретом режима. Новые install/update не запускаются.
- OUTSIDE_AVAILABILITY_SCOPE: локальный пользовательский проект под существующей отдельной политикой; результат не означает автоматического ALLOW.

Общие предусловия install/update/изменяющего repair: официальный scope известен, F=FRESH, M допускает действие, нет конфликтующей операции, выполняются текущие требования аккаунта и серверной выдачи конкретных разрешённых артефактов, metadata/paths/hash/trust соответствуют существующим границам. Проверка на сервере обязательна для официальных управляемых ресурсов; reachability badge её не заменяет.

Общие предусловия launch: установленная версия пригодна и не имеет незавершённой опасной транзакции; текущие требования аккаунта/профиля/ticket, целостности и безопасности выполняются; нет конфликтующего процесса; не нужен скрытый install/update. Обязательная security-политика допустимости версии, если применима, остаётся независимой. Сам факт наличия более новой версии не отменяет launch UNAVAILABLE или MAINTENANCE, если установленная версия удовлетворяет остальным условиям.

## 6. Матрица официальных действий

Ниже F=FRESH, scope известен, кроме отдельной строки UNKNOWN/STALE. «Условно» означает ALLOW_CONDITIONAL с предусловиями раздела 5. Repair здесь — изменяющий payload, в том числе скачивающий; локальная проверка целостности выделена отдельно.

| Режим/F | Install | Update | Изменяющий repair | Launch установленной игры | Stop работающей игры | Просмотр библиотеки/настроек/диагностики |
|---|---|---|---|---|---|---|
| INSTALL/FRESH | Условно | Условно | Условно | Условно | Доступен независимо от M/F | Доступен |
| BETA/FRESH | Условно, без персонального grant | Условно, без приглашения | Условно | Условно | Доступен независимо от M/F | Доступен |
| UNAVAILABLE/FRESH | DENY | DENY | DENY для загрузки/изменения payload | Условно: разрешён при остальных условиях, без install/update | Доступен независимо от M/F | Доступен |
| MAINTENANCE/FRESH | DENY | DENY | DENY для скачивания или изменения файлов | Условно: разрешён при остальных требованиях, без скрытых скачиваний/install/update | Доступен независимо от M/F | Доступен |
| Любой последний M при UNKNOWN/STALE | WAIT_FOR_EVIDENCE: fail-closed, не начинать | WAIT_FOR_EVIDENCE: fail-closed, не начинать | Не запускать новую изменяющую операцию до evidence | WAIT_FOR_EVIDENCE для нового официального запуска по предложению roadmap; требует review как отдельная freshness-политика | Доступен независимо от M/F | Доступен |

Локальная read-only проверка целостности не запрещается этими режимами, если использует существующие безопасные методы, не скачивает и не изменяет payload и не конфликтует с engine. «Просмотр настроек» не означает разрешение административной мутации или отключения защиты. Stop — доступность существующего управления процессом, не обещание мгновенного выхода и не право остановить произвольный чужой процесс.

Для launch UNKNOWN/STALE не вводится новая подтверждённая владельцем offline-политика: сохраняется предложенная roadmap потребность evidence, явно вынесенная на review. Нельзя использовать эту строку для ограничения независимых локальных проектов. Не подтверждённый freshness не следует объявлять UNAVAILABLE и затем выдавать launch по этому выдуманному режиму.

### Обязательный сценарий UNAVAILABLE и MAINTENANCE

При FRESH UNAVAILABLE или MAINTENANCE и готовой установленной версии кнопка «Играть» не отключается только из-за режима. Действие проходит обычные требования запуска и использует установленную версию. Если обнаружены отсутствующие Minecraft/JVM/loader/content файлы, вернуть конкретную причину «Для запуска нужны отсутствующие файлы. Установка сейчас недоступна» без скачивания и без изменения установки; автоматический install/update/repair не запускать. Нужна доказанная разделённость launch и install в engine: её отсутствие сейчас — технический блокер, а не основание переписать решение владельца.

Если обязательная независимая security-политика требует обновления, сообщить отдельно о несовместимости установленной версии и запрете update в текущем режиме; не обходить security и не заявлять, что любой UNAVAILABLE/MAINTENANCE launch запрещён.

## 7. Клиентские и серверные решения

| Решение | Ответственный и требуемое подтверждение | Недопустимая подмена |
|---|---|---|
| Какая кнопка и причина показаны | Клиент: единая чистая проекция всех состояний для native/HTML | Последний progress callback как независимый источник допуска |
| Наличие/целостность установленного | Клиентский существующий engine, безопасная проверка локального состояния | Наличие каталога, имя EXE или online badge |
| Допуск официального артефакта | Сервер: актуальная policy, artifact ID/action; клиент дополнительно проверяет metadata/bytes | UI label, публичный URL, поле tester |
| Действующая сессия/ticket | Сервер; клиент связывает ответ с текущей generation | Network success, локальный профиль или кэш старой сессии |
| Изменение глобального режима | Сервер: владелец/специальный admin, scoped RBAC каждой mutation, audit, CAS | Локальная роль, административный экран или снятие containment |
| Персональный BETA доступ | Не требуется: BETA открыта; общие проверки сохраняются | Создание новой системы приглашений |
| Уведомление о сети | Клиент: подтверждённые переходы, hysteresis/dedup | Ошибка одной загрузки как доказательство отсутствия Internet |
| Что значит MAINTENANCE launch | Решено владельцем: пригодная установленная игра запускается при остальных требованиях без загрузок/изменения установки | Общий запрет launch по режиму либо обход auth/security/integrity/version |

Мутация статуса требует проверки scope project/build/environment, живой сессии, explicit deny/revocation, expectedRevision/CAS, атомарного аудита и защиты cookie/bearer контекста. При неопределённом исходе не повторять запись вслепую. Имя permission, реализация idempotency и step-up — отдельный серверный дизайн. Текущий закрытый admin endpoint не считается готовым.

Public URLs открытой беты допустимы как публичное распространение, но не гарантируют серверный запрет прямых скачиваний после смены режима. Нужно отдельно выбрать границы: только официальный launcher path либо enforceable origin/CDN/Range/cache. Не обещать закрытый доступ или отзыв скачанных байтов.

## 8. Инварианты и будущие синтетические сценарии

Это спецификация будущих тестов; ни один сценарий сейчас не выполнен. Использовать искусственные состояния, fake clock/transport и события в памяти после отдельного разрешения. Никаких real downloads или mock-выводов о работоспособности Windows/production.

| Проверяемый инвариант | Синтетический сценарий и ожидаемое свойство |
|---|---|
| Измерения независимы | Health success + auth 401 + fresh UNAVAILABLE: N не даёт auth/installation, UNAVAILABLE не запрещает launch при выполнении прочих условий |
| UNAVAILABLE сохраняет launch | Готовая установленная версия + валидные остальные условия: launch ALLOW_CONDITIONAL; install/update/repair DENY; ни одного download intent |
| Отсутствие скрытой установки | UNAVAILABLE + missing JVM/loader/content: конкретный отказ из-за отсутствующих файлов, ноль intents install/update, данные сохранены |
| Более новая версия не равна непригодности | UPDATE_AVAILABLE + VERIFIED_READY: UNAVAILABLE не требует обновления; обязательная security restriction проверяется отдельно |
| Открытая BETA | Одинаковые общие условия у двух пользователей без grant: одинаковые права; отсутствие приглашения не причина отказа |
| MAINTENANCE launch решён владельцем | Пригодная установленная версия и выполненные прочие условия: launch ALLOW_CONDITIONAL; install/update/изменяющий repair DENY; stop/browse доступны |
| MAINTENANCE без скрытой загрузки | Missing Minecraft/JVM/loader/content: конкретная причина, завершение попытки без download intent или изменения установки; security/auth/integrity/version failure не обходится |
| UNKNOWN/STALE fail-closed | Нет status/TTL истёк: install/update не дают side-effect intent; кэш не становится OPEN; локальные проекты не получают эту политику |
| Изоляция scope/session | Поздний ответ аккаунта/окружения, неверный build ID, отсутствующая запись: не обновляют текущий допуск |
| Revision и expiry не продлеваются ошибкой | Старый ответ, конфликт одной revision, повтор с истёкшим validUntil, time uncertainty: нет нового FRESH по некорректному evidence |
| Отказ одного ресурса не равен offline | DNS/TLS/403/429/5xx: классификация Q корректна, C не переписывается, TLS fallback отсутствует |
| Outage не равен logout | Transport auth failure не создаёт session rejection и команды удаления credentials |
| UI единообразен | Одинаковый snapshot для native/HTML и alternate action: одно решение; progress не снимает DENY |
| Нет конфликтующих действий | ACTIVE/APPLYING/RECOVERY_REQUIRED: policy change не создаёт второй worker, cleanup или новый updater intent |
| Stop независим | RUNNING + каждый mode/F/auth: существующее stop action доступно; network loss не порождает автоматическое завершение |
| Восстановление без автодействий | Loss/recovery/flapping fake events: bounded уведомления, нет auto install/repair/login; late events игнорируются |
| Серверный RBAC обязателен | Искусственные scopes/roles/revocation/CAS: owner/admin проходят только действующую серверную проверку, остальные отказываются; это тест политики, не живого endpoint |
| Trust не зависит от availability | INSTALL/BETA + неверная подпись/metadata: отказ trust сохраняется; feed/keys/slots не меняются |

## 9. Зависимости и открытые вопросы

1. MAINTENANCE launch — RESOLVED_BY_OWNER. Это закрывает только выбор режима, не технические доказательства его корректной реализации и не остальные вопросы этапа A.
2. Freshness-политика официального launch при UNKNOWN/STALE требует review; fail-closed новых install/update фиксирован этим заданием. Полноценный offline launch не подтверждён.
3. Точные TTL/skew/cache, границы доверия к часам, persistence revision и правила повреждённого кэша не утверждены. Параметры из roadmap остаются предложениями.
4. Нужны достоверный official ID/environment map и поддерживаемые версии EXE. Legacy CLOSED может блокировать launch, разрешённый новым UNAVAILABLE; нельзя механически перенести старое поведение.
5. Требуется доказать launch без скрытого install/update и не нарушить safe recovery. В MAINTENANCE repair со скачиванием или изменением файлов запрещён решением владельца. Разделение read-only проверки, изменяющего repair и обязательного recovery требует классификации реальных операций; repair в UNAVAILABLE по-прежнему включить в review владельца.
6. Безопасный admin write endpoint и production freshness-контракт не подтверждены. Локальный source не доказывает deployed состояние.
7. Нужен выбор границ enforcement публичных URL и проверка всех official manifest/archive/files/Range/runtime/loader paths и альтернативных UI actions.
8. Серверная привязка game ticket к build и совместимость обработчика игры не доказаны. Открытая BETA не требует персональных grants.
9. OS/Qt reachability backend, health route без записей, параметры hysteresis/backoff/cooldown ещё требуют проектирования. Deadline не обещает hard timeout системного I/O.

### Как закрываются оставшиеся блокеры этапа A

| Блокер | Что можно решить документальным review | Что требует отдельного исследования/разрешения |
|---|---|---|
| Freshness launch при UNKNOWN/STALE | Утвердить launch-политику отдельно от уже принятого MAINTENANCE/UNAVAILABLE и fail-closed install/update | Проверить существующий ticket/status flow и доказательства свежести; код/тесты только по отдельному scope |
| TTL и доверие к часам | Выбрать TTL/skew, cache/restart и поведение при неопределённом времени | Подтвердить server timestamps, monotonic/persistence поведение и recovery; тесты/запросы отдельно |
| Классификация repair | Зафиксировать различие read-only/изменяющий repair/recovery; утвердить оставшуюся политику UNAVAILABLE | Прочитать конкретные пути engine и доказать отсутствие записей/скачиваний; никакого автоматического запуска экспериментов |
| Scope официальных ресурсов | Согласовать границу official/local и требования enforcement | Подтвердить все IDs/manifest/archive/Range/runtime/loader и UI routes отдельным аудитом; live-проверки только с разрешением |
| Старые клиенты | Определить поддерживаемые версии и допустимый контракт совместимости | Проверить реальные legacy action paths без переименования CLOSED в новое поведение; сборки/запуски не разрешены |
| Неподтверждённые серверные гарантии | Зафиксировать необходимые schema/RBAC/audit/CAS/delivery требования и критерии | Отдельно подтвердить source/deployment соответствие и API/trust guarantees; production/DB/deploy не входят в документальный этап |

Документальный выбор требования не доказывает свойства реализации. Техническое исследование сначала должно быть разрешено в конкретном read-only scope; реализация, тесты и любые живые операции требуют собственного разрешения.

## 10. Критерии готовности этапа A и запрет автоматического перехода

Документальная часть подготовлена, MAINTENANCE launch решён владельцем, но этап A целиком не объявляется завершённым. Для готовности нужны: review терминов и переходов; согласование оставшихся freshness/repair правил; подтверждённый scope официальных ресурсов и список технических зависимостей/ограничений старых клиентов; отсутствие противоречий трём прежним решениям владельца и новому решению MAINTENANCE. Необязательно разрешать production-аудит ради согласования документа: неподтверждённые факты должны оставаться блокерами последующих этапов. Переход к B этим изменением не разрешён.

После review — только отдельное разрешение на чистую модель этапа B и её конкретные синтетические тесты. Этот контракт не разрешает реализацию, тесты, API, миграции, deployment, выдачу прав, приложение или загрузки.

Границы установщика/обновления сохраняются: существующие path/pinning, transaction/recovery, install ownership, slots/rollback, HTTPS/origin policy, release signatures и TUF. Availability не разрешает код и не меняет trust stores stable/beta или bootstrap feed. SHA-256 не заменяет цифровую подпись автора. Windows/trust/installer блокеры не закрыты документом.
